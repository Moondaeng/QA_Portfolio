# AI Helpy Chat Firefox UI 자동화 테스트

Selenium과 pytest로 AI 채팅 서비스의 핵심 사용자 흐름을 검증한 자동화 프로젝트입니다.  
사용자가 가장 오래 머무르고 여러 기능이 연결되는 **AI 응답 영역을 가장 영향도가 큰 지점**으로 판단해 우선 자동화했습니다.

> 이 저장소에는 3인 팀 프로젝트 중 제가 담당한 **Firefox 자동화 코드와 프로젝트 종료 후 개선한 POM 구조**만 담았습니다.

## 테스트 우선순위를 정한 이유

AI 채팅 서비스에서 가장 큰 장애는 사용자가 질문을 전송했지만 AI 응답을 받지 못하는 상황이라고 판단했습니다.

- AI 응답은 서비스의 핵심 기능입니다.
- 사용자가 가장 많은 시간을 보내는 영역이라 반복 검증 필요성이 높습니다.
- 질문 전송, 웹 검색, 이미지 생성, 추천 질문, 응답 복사와 재생성 등 여러 기능이 AI 대화에 연결됩니다.
- 응답 완료 상태를 반복해서 확인할 필요가 있어 자동화 대상으로 선정했습니다.

따라서 **장애 영향도와 반복 실행 빈도**를 우선 기준으로 삼아 AI 대화 흐름부터 자동화했습니다.

## 프로젝트 배경과 담당 역할

팀 프로젝트에서는 Chrome, Edge, Firefox 담당자가 합의한 핵심 흐름을 각 브라우저에 맞게 구현했습니다.  
저는 Firefox 영역에서 다음 작업을 담당했습니다.

- Firefox WebDriver와 pytest 실행 환경 구성
- Firefox 기준 TC 항목 자동화 및 네 개의 pytest 시나리오 작성
- 로그인, 새 대화, AI 응답, 사이드바, 에이전트 생성 Page Object 구현
- Firefox 코드에 POM을 적용해 Locator·페이지 동작·테스트 시나리오 분리
- 공통 대기·클릭·호버·스크롤 동작을 `BasePage`로 분리
- React·MUI·Virtuoso 환경의 중복 DOM과 내부 스크롤 문제 대응
- 팀 내 코드 작성 규칙과 클래스 역할 설명 문서화
- 실행 시각별 로그 기록과 최종 실행 영상 제작

프로젝트 종료 후에는 이 저장소의 코드를 다음 프로젝트에서도 참고할 수 있도록 [`BasePage`](./src/firefoxPages/base_page.py)를 개선했습니다.  
페이지별 동작과 공통 Selenium 동작의 책임을 다시 나누고, 대기·재시도·선택적 요소 처리와 메서드 반환값을 정리했습니다.

### 회원가입 1개·로그인 검증 9개의 TC 항목

회원가입은 신규 사용자에게 중요하지만 일반 사용자가 반복적으로 수행하는 기능은 아니라고 판단해 후순위로 배치했습니다.  
로그인 검증은 핵심 E2E 시나리오를 먼저 완성하기 위해 후순위로 배치했습니다.
로그인 성공 흐름은 네 개 테스트가 서비스에 진입하기 위한 공통 단계로 포함했습니다.  
팀원들과 합의한 핵심 사용자 흐름은 각 브라우저의 E2E 테스트에 먼저 반영했습니다.

프로젝트 중에는 예상보다 다음 작업에 많은 시간이 필요했습니다.

- React·MUI의 중복 DOM과 Hidden Element 원인 분석
- 오버레이, 모달 등의 클릭 방해, 포커스와 내부 스크롤 문제 해결
- POM의 재사용성·가독성·캡슐화 범위 결정 및 구현

제한된 기간에 핵심 경로의 구현과 안정화를 우선하면서 회원가입 1개와 로그인 검증 9개는 최종적으로 구현하지 못했습니다.

## 자동화 설계와 판단

### POM과 BasePage

테스트 코드에는 사용자 시나리오를 남기고 Selenium의 세부 동작은 Page Object에 배치했습니다.

```text
Test                 사용자 흐름과 실행 순서
  └─ Page Object     화면별 Locator와 사용자 동작
       └─ BasePage   탐색·대기·클릭·호버·스크롤 등 공통 처리
```

`BasePage`의 주요 역할은 다음과 같습니다.

- visible·clickable·present·invisible 상태별 명시적 대기
- 중복 요소 중 화면에 표시된 첫 요소 선택
- Stale Element와 클릭 가로채기 발생 시 요소 재조회 및 재시도
- 없어도 정상인 팝업과 버튼을 위한 선택적 클릭
- 목록 인덱스 검증과 동적 목록 재조회
- 마우스 포인터 이동과 요소 중앙 정렬
- 브라우저 문서와 내부 스크롤 컨테이너를 구분한 스크롤 처리

### 상태를 기준으로 한 AI 응답 대기

초기에는 응답 시간을 예상해 고정 대기를 사용했지만 네트워크와 생성 시간에 따라 테스트가 불안정했습니다.  
이후 AI 생성 중 표시되는 취소 버튼을 기준으로 다음 상태를 순서대로 기다리도록 변경했습니다.

1. 취소 버튼이 DOM에 나타남
2. AI 응답 생성이 끝나 취소 버튼이 사라짐
3. 다음 사용자 동작 수행

이 방식으로 “몇 초를 기다릴지”가 아니라 “어떤 상태가 완료되어야 하는지”를 기준으로 대기했습니다.

### Hidden Element와 중복 DOM 처리

React·MUI 화면에서는 같은 Locator를 가진 요소가 DOM에 여러 개 존재해 숨겨진 요소가 먼저 선택되는 문제가 있었습니다. Locator만 반복해서 바꾸는 방식으로는 해결되지 않았습니다.

`find_elements()`로 후보를 수집한 뒤 `is_displayed()`를 만족하는 요소를 제한 시간 동안 다시 찾는 `wait_for_first_visible()`을 구현했습니다. Stale Element가 발생하면 해당 요소를 버리고 다시 조회해 화면에 실제로 표시된 대상을 선택했습니다.

### 클릭과 포커스 문제

요소를 찾았지만 오버레이, 애니메이션, 포커스와 화면 위치 때문에 `ElementClickInterceptedException`이 발생했습니다.

- 클릭 가능한 상태를 먼저 확인
- 실패 시 같은 WebElement를 재사용하지 않고 Locator로 다시 조회
- 메인 영역으로 포인터를 이동해 호버 메뉴와 오버레이 상태 정리
- 화면 밖 요소는 중앙으로 이동한 뒤 클릭
- JavaScript 클릭은 실제 사용자 동작과 다를 수 있어 최후 수단으로 제한

### Virtual Scroll 처리

사이드바는 브라우저 문서가 아니라 `virtuoso-scroller` 내부가 스크롤되는 구조였습니다. `window.scrollTo()`가 동작하지 않아 스크롤 컨테이너의 `scrollTop`을 직접 변경하는 방식으로 전환했습니다.

범용 `BasePage`에는 window 스크롤 헬퍼도 남겨 두었지만, 대상 서비스에서는 내부 컨테이너 스크롤을 사용했기 때문에 최종 테스트 시나리오에는 포함하지 않았습니다.

## 현재 실행 제약

이 프로젝트가 사용한 개발 서버는 현재 종료되어 같은 환경에서 다시 실행할 수 없습니다.  
따라서 현재 저장소는 실행 가능한 데모 서비스가 아니라 다음 근거를 함께 보존한 포트폴리오 아카이브입니다.

- 서버 종료 전 최종 시나리오에서 사용한 Page Object 메서드의 동작 확인
- 네 개 자동화 시나리오의 최종 전체 통과 영상
- 실행 단계와 완료 시각이 남은 로그
- 프로젝트 종료 후 범용성을 높인 `BasePage` 코드

단, window 기반 스크롤 메서드는 대상 서비스 구조상 최종 시나리오에서 사용하지 않았으므로 프로젝트 종료 후 버전에서 다시 검증하지 못했습니다.

## 남아 있는 한계와 개선 계획

1. **검증 조건 강화**
   현재 테스트는 명시적 대기 실패, Selenium 예외와 화면 상태 변화를 중심으로 실패를 판단합니다. 다음 프로젝트에서는 Page Object가 상태를 반환하고 테스트가 기대 결과를 명시적인 `assert`로 검증하도록 개선할 계획입니다.
2. **실패 증적 자동 수집**
   실행 로그에 더해 실패 시 URL, 오류 메시지와 스크린샷을 자동으로 저장하도록 pytest Hook을 확장할 계획입니다.
3. **Locator 정리**
   대부분 의미 있는 속성과 상대 XPath를 사용했지만 샘플 질문에는 동적으로 보일 수 있는 class Locator가 남아 있습니다.  
    서비스에 안정적인 테스트 속성이 제공된다면 `data-testid`나 'id' 같은 명확한 속성으로 교체할 계획입니다.

## 프로젝트에서 배운 점

- 자동화 개수보다 장애 영향도와 반복 빈도를 기준으로 대상을 선택하는 것이 중요했습니다.
- 불안정한 테스트를 단순히 기다리게 만들기보다 DOM과 화면 상태의 차이를 분석해야 했습니다.
- POM은 파일을 여러 개로 나누는 방식이 아니라 테스트·페이지 기능·공통 동작의 책임을 구분하는 설계였습니다.
- 모든 예외를 처리해 테스트를 통과시키는 것보다 실제 실패를 숨기지 않는 기준이 중요했습니다.
- 요구사항을 확인하지 못한 현상은 결함으로 단정하지 않고 사실, 추측과 잔여 위험을 구분해야 했습니다.
