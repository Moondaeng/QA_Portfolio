# 하위 영역 README 작성 가이드

## 1. 문서 목적

이 문서는 UI, API, CI/Jenkins, JMeter 등 하위 영역 README를 작성할 때 팀원과 AI 도구가 함께 따르는 공용 기준입니다.

루트 `README.md`는 프로젝트 전체를 3분 안에 이해할 수 있게 요약하고, 하위 README는 각 영역의 목적, 설계, 실행 방법, 결과와 문제 해결 과정을 실제 근거를 바탕으로 설명합니다.

## 2. 기본 원칙

- 저장소의 실제 코드, 설정, 테스트 결과와 팀이 확인한 자료만 근거로 작성합니다.
- 확인되지 않은 수치, 기능, 실행 조건과 성과를 추측하지 않습니다.
- 일부 테스트에만 적용된 구현을 전체 영역의 공통 특성처럼 표현하지 않습니다.
- 사용하지 않은 기술, 추가하지 않은 기능과 제외 사유처럼 현재 주제의 이해에 필요하지 않은 설명은 넣지 않습니다.
- 설치 중심의 초기 협업 가이드보다 현재 프로젝트를 실행하고 검증하는 방법을 우선합니다.
- 메인 README의 설명을 그대로 반복하지 않고, 요약 후 필요한 상세 내용을 제공합니다.
- 전문 용어와 약어는 처음 의미가 달라질 수 있으면 처음 등장할 때 프로젝트에서의 의미를 설명합니다.
- 미완성 문서나 공유할 수 없는 자료에 빈 링크를 만들지 않습니다. 필요한 경우 `추가 예정`으로 표시합니다.
- 문서 제목과 표의 용어는 같은 개념에 일관되게 사용합니다.

## 3. 권장 구성

영역의 특성에 따라 순서를 조정할 수 있지만 다음 내용을 우선 검토합니다.

### 3.1 영역 개요

- 이 영역이 해결하려는 문제
- 프로젝트 전체에서 담당하는 검증 범위
- 다른 테스트 영역과 구분되는 역할

### 3.2 검증 범위

- 주요 사용자 흐름, API 계약, 파이프라인 또는 성능 시나리오
- 포함 범위와 우선순위
- 테스트 수, TC 수와 같은 수치는 기준 시점과 집계 범위를 함께 명시

### 3.3 구조와 설계

- 디렉터리와 모듈이 나뉜 이유
- 테스트, Page Object, API Client, fixture와 설정 파일의 책임
- 재사용성, 독립성, 추적성과 안전성을 높인 대표 설계
- 구조가 복잡하면 다이어그램을 사용하고, 단순한 목록은 표나 짧은 트리로 표현

### 3.4 실행 시나리오

명령어만 나열하지 않고 실행 목적과 기대 결과를 함께 작성합니다.

| 시나리오 | 실행 명령 또는 조건 | 기대 결과 |
| --- | --- | --- |
| 예시 | `poetry run pytest ...` | 실행 대상, 판정 기준과 생성되는 결과물 |

- 저장소에서 실제로 동작하는 명령만 사용합니다.
- 계정, 토큰, URL과 같은 비밀정보를 예시에 직접 작성하지 않습니다.
- 기관 승인이나 지정 환경이 필요한 실행은 승인 주체와 안전 조건을 명시합니다.

### 3.5 대표 설계와 코드

- 영역의 장점을 가장 잘 설명하는 코드 1~3개를 선정합니다.
- 코드가 해결한 문제, 적용 범위와 결과를 먼저 설명합니다.
- 짧은 스니펫과 저장소의 원본 파일 링크를 함께 제공합니다.
- 긴 파일 전체나 설명 없는 코드를 붙여 넣지 않습니다.
- cleanup, retry, fallback처럼 조건부로 적용된 로직은 실제 적용 범위를 정확히 밝힙니다.
- 클릭이나 함수 반환보다 사용자가 확인하는 최종 상태, 응답 계약 또는 파이프라인 결과를 어떻게 검증하는지 보여줍니다.

### 3.6 결과와 증적

- 테스트 수, 통과 결과, 실행 시간과 성능 지표 중 영역을 대표하는 수치만 사용합니다.
- 전체 실행과 특정 실행 결과를 구분하고 실패 결과를 임의로 제외하거나 PASS로 보정하지 않습니다.
- 보고서, 로그, Allure, JUnit, 스크린샷 등 제3자가 확인할 수 있는 증적을 연결합니다.
- 링크를 공유할 수 없거나 아직 준비되지 않았다면 링크 대신 `추가 예정`으로 표시합니다.

### 3.7 한계와 개선 방향

- 한계는 변명이 아니라 확인된 제약과 그 영향을 설명합니다.
- 서로 원인이 다른 한계는 한 문장이나 한 행에 합치지 않습니다.
- 개선 방향은 추상적인 다짐보다 다음 작업에서 실행할 수 있는 행동으로 작성합니다.
- `한계 → 영향 → 개선 행동`의 연결이 자연스러운지 확인합니다.

## 4. 영역별 필수 확인 사항

### 4.1 UI 자동화

- 학습자·교육자 검증 범위와 대표 사용자 흐름
- Page Object와 테스트 코드의 책임 분리
- WebDriver fixture, 대기 조건과 테스트 독립성
- 생성·수정·삭제 데이터의 준비와 정리 기준
- 로컬 GUI와 CI Headless 실행 환경의 차이
- 브라우저와 운영체제 검증 범위를 실제 수행 결과에 맞게 명시

### 4.2 API 자동화

- endpoint 또는 기능별 검증 범위
- Client 계층과 테스트 계층의 책임
- 인증, timeout, 상태 코드, schema, 필수 필드와 권한 검증
- 생성 데이터의 독립성과 정리 기준
- 재시도 및 fail-fast 정책
- 요청·응답 로그의 민감정보 보호 기준

### 4.3 CI/Jenkins

- Job별 실행 대상과 트리거
- MR, 새 커밋과 수동 실행 조건의 구분
- worker와 동시 빌드 제한
- Credentials와 외부 연동 정보 관리
- 테스트 판정, 결과 게시와 Artifact 보관 흐름
- Jenkins를 구축한 환경과 현재 확인에 필요한 명령

### 4.4 JMeter

- 테스트 목적과 대상 환경
- 기관 승인 주체, 허용된 VU·Loop·실행 시간과 중단 기준
- 단계별 부하 증가 조건과 이전 단계 통과 기준
- 목표 VU와 실제 동시 활성 사용자 수를 구분
- 오류율, 응답 시간, 처리량과 서버 상태 결과
- 보수적인 설정이 결과에 미친 영향과 재검증 조건

### 4.5 수동·탐색적 테스트와 이슈

- 요구사항 분석 및 In Scope 선정 기준
- 수동 검증 범위와 완료 수치
- 자동화 검토 범위와 제외 범위를 구분
- Jira Priority 또는 Severity의 출처
- 주요 이슈의 사용자 영향과 재현·추적 자료

## 5. 시각화 기준

- 구조, 파이프라인과 여러 단계의 관계는 다이어그램으로 표현합니다.
- 수치 비교, 실행 조건과 역할 구분은 표를 사용합니다.
- 이미지는 장식보다 정보 전달을 목적으로 사용합니다.
- 이미지 안의 수치와 명칭은 본문 및 실제 설정과 일치해야 합니다.
- SVG와 이미지에는 내용을 설명하는 대체 텍스트를 제공합니다.
- 글자가 작거나 정보가 과도한 이미지는 여러 개로 나눕니다.

## 6. 안전과 보안

각 영역은 해당되는 안전 설계를 설명합니다.

- 동시성 통제: worker, thread, VU와 동시 빌드 상한
- 호출 빈도 상한: 요청 간격, ramp-up, Loop 제한
- 재시도 정책: 허용 조건, 최대 횟수와 fail-fast 기준
- 실행 시점 통제: MR, 수동 실행, 기관 승인과 지정 시간
- 데이터 보호: 고유 테스트 데이터와 대상 한정 cleanup
- 비밀정보 보호: 환경변수와 Jenkins Credentials 사용, 로그 마스킹

안전 조건은 예시가 아니라 실제 코드와 설정에서 확인된 값으로 작성합니다.

## 7. 메인 README와 연결

- 메인 README에는 하위 영역의 목적, 대표 성과와 상세 README 링크만 남깁니다.
- 하위 README 첫 부분에서 프로젝트 전체가 필요하면 루트 README로 연결합니다.
- 같은 수치를 두 문서에 사용하면 집계 범위와 기준을 동일하게 유지합니다.
- 하위 문서의 변경으로 전체 구조나 핵심 수치가 바뀌면 메인 README와 시각 자료도 함께 점검합니다.

## 8. 작성 및 검토 절차

1. 코드, 설정, TC와 결과 보고서에서 확인 가능한 사실을 수집합니다.
2. 부족한 자료와 확인이 필요한 표현을 팀에 먼저 질문합니다.
3. 영역의 목적과 독자가 먼저 알아야 할 내용을 정합니다.
4. 권장 구성을 사용해 초안을 작성합니다.
5. 명령어, 링크, 파일 경로, 수치와 이미지 내용을 실제 저장소 기준으로 검증합니다.
6. 메인 README 및 다른 하위 README와 중복되거나 충돌하는 설명을 정리합니다.
7. 담당 영역을 모르는 팀원도 목적, 실행 결과와 설계 장점을 이해할 수 있는지 검토합니다.
