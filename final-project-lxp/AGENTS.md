# LXP 테스트 자동화 프로젝트 지침

## 문서 목적

- 이 문서는 learner, educator, API 등 특정 담당자의 소유권을 정하는 문서가 아니다.
- 모든 팀원과 AI 도구가 같은 구조, 안전 기준과 협업 절차를 따르기 위한 공용 지침이다.
- 실제 작업 영역, 대상 TC, 수정 가능 범위와 보호 범위는 각 작업 요청에서 정한다.
- 문서의 영역별 예시는 고정된 담당자 배정이 아니라 코드 위치와 영향 범위를 설명한다.
- 요청에 작업 범위가 명확히 지정되면 해당 범위를 우선하며, 공용 파일 변경이나 범위 확장이 필요하면 먼저 협의한다.

## 문서 체계

- `README.md`: 모든 팀원이 처음 확인하는 프로젝트 사용 안내다.
- `AGENTS.md`: 모든 팀원과 AI 도구가 현재 따라야 하는 개발·협업 규칙이다.
- [예외 처리 기준](./docs/EXCEPTION_HANDLING.md): UI와 API 자동화에서 사용하는 예외 유형, 반환값, 재시도와 fallback의 상세 기준이다.
- `Safety_Design.md`: UI, API, 수동 및 성능 테스트 실행자 모두에게 적용되는 안전 규칙이다.
- 영역별 README: 해당 코드 계층의 작성 방법을 설명하며 담당자 소유권을 지정하지 않는다.
- 문서 간 내용이 충돌하면 운영 안전 규칙, 현재 작업 요청, AGENTS.md, 영역별 참고 문서 순서로 확인하고 필요한 경우 팀에 질문한다.

## 프로젝트 방향

- Python과 pytest를 공통 테스트 기반으로 사용한다.
- Selenium은 UI 자동화에만 사용한다.
- 긴 E2E보다 독립적인 기능 테스트를 작성한다.
- 기존 TC 범위를 임의로 확장하지 않는다.
- 테스트마다 검증하는 TC ID를 명시한다.

## 코드 역할

- 테스트 코드는 사용자 흐름과 명시적인 assert를 담당한다.
- Page Object는 Locator, 화면 조작, 화면 정보 조회를 담당한다.
- BasePage는 여러 Page에서 실제로 공통인 기능만 담당한다.
- 로그인은 `pages/login_page.py`를 공통으로 사용한다.
- 학습자와 교육자 코드는 각각의 폴더로 구분한다.
- Page Object 메서드는 특정 TC보다 재사용 가능한 사용자 동작을 표현한다.
- 한 Page에서만 반복되는 판별 로직은 해당 Page의 private 메서드로 추출한다.

## 테스트 독립성과 Fixture

- 별도 지시가 없다면 각 테스트는 이전 테스트의 실행 상태에 의존하지 않는다.
- UI 테스트의 WebDriver는 기본적으로 function scope를 사용한다.
- module 또는 session scope를 사용할 때는 쿠키, 로그인, URL 및 저장소 상태의 초기화 기준을 함께 정의한다.
- 브라우저 재사용을 위한 쿠키 삭제나 강제 URL 이동은 명확한 요구사항 없이 추가하지 않는다.
- 역할 전용 driver와 기존 공용 driver fixture의 옵션과 scope를 임의로 함께 변경하지 않는다.
- 로그아웃 테스트는 새 브라우저의 비로그인 상태를 기본으로 사용한다.

## 로그인과 인증

- 일반 로그인과 서비스 이용 중 발생하는 비밀번호 재인증을 구분한다.
- 로그인 fixture는 로그인 완료와 대상 화면 진입까지 보장한 후 driver를 반환한다.
- 재인증 처리는 재인증 화면이 실제로 확인된 경우에만 수행한다.
- 테스트마다 새 브라우저를 사용하면 이전 세션을 전제로 한 쿠키 및 저장소 초기화 코드를 추가하지 않는다.
- 로그인 실패를 재인증이나 URL 직접 이동으로 임의 보완하지 않는다.

## Locator

- MUI의 동적 CSS 클래스는 사용하지 않는다.
- `aria-label`, `name`, `data-testid`, 안정적인 `href`와 텍스트를 우선한다.
- Locator 타입은 `변수명: Locator = (...)` 형식으로 작성한다.
- 숨겨진 중복 DOM이 있으면 화면에 보이는 요소를 선택한다.
- `body` 전체 텍스트보다 검증 대상 영역의 구체적인 요소를 우선 조회한다.

## 대기와 Flaky 테스트 대응

- 요소 상태는 고정 sleep보다 WebDriverWait와 명시적인 화면 완료 조건으로 기다린다.
- StaleElementReferenceException 등 일시적인 DOM 변경에만 제한적으로 재시도를 적용한다.
- 재시도는 동일한 사용자 동작을 반복해도 안전한 경우에만 적용한다.
- URL 직접 이동, JavaScript 강제 클릭, 반복 클릭은 기대 동작이 명확할 때만 사용한다.
- 화면 전환 실패의 기대 동작이나 수정 기준이 명확하지 않으면 임의로 우회하지 않고 요청자 또는 관련 팀원에게 확인한다.
- TimeoutException을 광범위한 Exception 처리로 숨기지 않는다.
- 화면 전환 완료는 목적지의 URL 또는 고유 요소처럼 전환을 직접 입증하는 조건으로 확인한다. 삭제처럼 이전 상태의 잔존 여부가 중요한 동작은 목적지 확인과 이전 DOM 제거를 함께 확인한다.
- 조건부 재시도는 현재 화면이 알려진 복구 가능 상태임을 확인한 뒤 최대 한 번만 수행한다.

## TC 구성

- 여러 TC ID를 한 테스트에서 검증하려면 동일한 사용자 흐름과 화면 상태에서 모두 확인할 수 있어야 한다.
- TC를 합친다는 이유로 동일한 스크롤, 화면 진입 또는 버튼 클릭을 반복하지 않는다.
- 서로 다른 사전 조건이나 독립적인 상태 변경이 필요한 TC는 별도 테스트로 유지한다.
- boolean과 숫자 테스트 데이터는 의미를 알 수 있는 이름의 상수 또는 데이터 객체로 표현한다.
- 동작, 요소 대기와 결과 검증을 분리해 실패한 단계를 알 수 있게 작성한다.
- 대기 메서드가 이미 보이는 요소 반환을 보장하면 같은 가시성 검증을 불필요하게 반복하지 않는다.
- `current_url`의 존재 여부가 아니라 기대하는 도메인, 경로, 쿼리 또는 화면 고유 요소를 검증한다.
- 부재를 검증하기 전 대상 화면의 로딩 완료와 검색 범위를 먼저 보장한다.
- 여러 허용 결과를 `or`로 검증할 때는 요구사항이 실제로 대체 결과를 허용하는지 확인하고 각 조건을 실패 메시지에 남긴다.
- Page Object 메서드가 성공 시 항상 값을 반환하고 실패 시 예외를 발생시키는 구조라면 반환값의 `is not None`을 검증하지 않는다.
- 생성·수정·삭제 테스트는 클릭 결과나 반환값이 아니라 상세 화면의 제목·내용 등 사용자가 확인할 수 있는 최종 상태를 검증한다.
- 테스트 주석의 기대 결과와 실제 `assert` 대상은 일치해야 하며, 최종 결과를 검증해야 하는 TC를 중간 동작 성공만으로 통과시키지 않는다.
- 실행별 고유 데이터를 검증할 때는 대상 컨테이너 안에서 완전 일치를 우선해 이전 실행 데이터에 의한 오탐을 방지한다.

## 테스트 상태와 데이터

- 학습 시작과 이어서 학습처럼 사전 상태가 다른 시나리오는 독립적으로 준비하고 검증한다.
- 앞 테스트가 만든 상태나 실행 순서에 의존해 다음 테스트를 통과시키지 않는다.
- 고정 URL과 변동 가능한 화면 데이터는 별도로 관리한다.
- 목록의 첫 페이지나 특정 순서에 공유 데이터가 항상 존재한다고 가정하지 않는다.
- 생성 데이터는 실행마다 식별 가능한 고유 ID 또는 고유 값으로 구분하고 해당 데이터만 정리한다.
- cleanup은 가능하면 yield fixture로 분리해 테스트 본문 실패와 teardown 실패를 구분한다.
- cleanup 실패를 `except Exception: pass`로 숨기지 않는다.

## API 자동화

- API 요청 코드는 테스트에서 반복하지 않고 `api/clients/`의 Client 계층으로 분리한다.
- API Client는 URL, 헤더, 파라미터와 payload 구성 및 응답 반환을 담당한다.
- 테스트는 상태 코드, 응답 schema, 핵심 필드와 비즈니스 결과를 명시적으로 assert한다.
- endpoint, 인증 토큰과 계정 정보는 환경변수 또는 fixture로 제공한다.
- 모든 API 요청에는 명시적인 timeout을 설정한다.
- 생성·수정·삭제 테스트는 독립 실행과 생성 데이터 정리 기준을 갖춰야 한다.
- 재시도는 일시적인 네트워크 장애나 명확한 eventual consistency에만 제한적으로 적용한다.
- 요청 및 응답 로그에 Authorization, Cookie, 비밀번호와 개인정보를 기록하지 않는다.

## 로그와 오류 기록

- Page Object의 주요 사용자 동작은 INFO 수준으로 기록한다.
- 로그 이름은 모듈 경로를 기준으로 구분할 수 있어야 한다.
- 일반 실행 로그와 실패 traceback 로그는 별도 파일로 저장한다.
- 비밀번호, 이메일 원문, 토큰과 쿠키는 로그에 기록하지 않는다.
- fallback, 재시도 또는 예외 무시가 발생하면 원인과 횟수를 적절한 로그 수준으로 남긴다.
- 복구 가능한 첫 실패는 `WARNING`, 재시도 후 최종 실패나 복구 불가능한 실패는 `ERROR`로 기록한다.
- 필수 환경 설정 누락, 잘못된 함수 인자, Selenium 대기 실패와 테스트 기대 결과 불일치를 서로 다른 실패로 유지한다.
- 처리할 수 있는 구체적인 예외만 잡고 예상하지 못한 예외는 그대로 전달한다.
- 예외를 기록한 뒤 다시 전달하는 경계에서는 `logger.exception()` 또는 `exc_info=True`를 사용해 traceback을 보존한다.
- 예외 유형, `None`·`False` 반환, 재시도, fallback과 Page Object의 `assert` 사용에 관한 상세 기준은 [예외 처리 기준](./docs/EXCEPTION_HANDLING.md)을 따른다.

## UI 상태 판별

- 네이티브 checkbox는 `is_selected()`로 현재 상태를 확인한다.
- ARIA switch 또는 checkbox는 `aria-checked`, 토글 버튼은 `aria-pressed`를 정확히 비교한다.
- `outerHTML`에서 `checked` 문자열의 포함 여부로 상태를 판단하지 않는다.
- CSS 말줄임표와 DOM 텍스트가 같다고 가정하지 않고 실제 DOM과 검증 목적을 확인한다.
- 텍스트 비교는 대상 카드, 게시글 또는 상세 영역으로 범위를 제한한다.
- 완전 일치, 부분 일치, `textContent` 또는 `title` 속성 중 무엇을 사용할지는 화면 구현과 요구사항에 따라 결정한다.

## 브라우저 화면 조건

- 기본 창 크기와 위치는 WebDriver fixture에서 관리한다.
- 공유 driver에서 창 크기나 위치를 바꾸면 teardown에서 기존 값을 복원한다.
- 좌우 배치 등 시연 목적의 화면 조작은 기능 검증과 분리한다.

## 협업과 변경 범위

- 학습자 UI 코드는 `pages/learner/`와 `tests/learner/`에 배치한다.
- 교육자 UI 코드는 `pages/educator/`와 `tests/educator/`에 배치한다.
- API Client는 `api/clients/`, API 테스트는 `tests/api/`에 배치한다.
- 파일 위치는 담당자 소유권을 의미하지 않으며 팀원이 합의된 작업 범위에 따라 어느 영역이든 작업할 수 있다.
- `tests/conftest.py`, `pages/base_page.py`, `pages/login_page.py` 변경 시 양쪽 영향을 확인한다.
- 다른 팀원이 작업 중인 파일, fixture 이름과 기존 호출 방식은 합의 없이 변경하지 않는다.
- merge 충돌은 한쪽 파일 전체를 선택하지 않고 양쪽에만 있는 fixture, hook과 설정을 비교해 해결한다.
- 문제 원인과 기대 동작이 명확하지 않으면 추측으로 수정하지 않고 요청자 또는 관련 팀원에게 확인한다.
- 작업과 무관한 기존 변경이나 미추적 파일을 삭제하거나 되돌리지 않는다.
- 일회성 검증을 위해 추가한 marker는 지속적인 실행 전략으로 합의되지 않았다면 커밋 전에 제거한다.

## AI 작업 요청 해석

- README의 AI 요청 문구는 자리표시자 예시이며 learner 또는 educator를 기본 담당으로 가정하지 않는다.
- AI는 매 요청에서 지정된 작업 영역, TC 또는 작업 목적, 수정 가능 범위와 보호 범위를 먼저 확인한다.
- 특정 영역이 지정되지 않았으면 변경 전에 영향 범위를 조사하고 필요한 경우 요청자에게 확인한다.
- “공용 문서”, “공용 규칙”과 “공용 구조” 작업은 역할별 코드 소유권과 분리해 팀 전체 관점에서 검토한다.
- 동시에 진행 중인 작업이나 충돌 가능성이 알려진 파일은 명시적인 허용 없이 수정하지 않는다.

## 브랜치와 변경 단위

- `feature/`: 새 기능이나 새로운 TC를 추가할 때 사용한다.
- `fix/`: 기존 기능이나 테스트 코드의 오류를 수정할 때 사용한다.
- `hotfix/`: 배포·실행을 막는 긴급 문제를 즉시 수정할 때 사용한다.
- `docs/`: 코드 동작 변경 없이 문서나 공용 지침을 정리할 때 사용한다.
- `chore/`: 설정, 디렉터리 구조, 의존성 등 유지보수 작업에 사용한다.
- `refactor/`: 외부 동작은 유지하면서 코드 구조나 공통 기능을 개선할 때 사용한다.
- 하나의 브랜치는 하나의 검토 가능한 목적을 갖도록 유지한다.
- 서로 독립적인 기능, 문서와 구조 변경은 가능한 한 별도 브랜치와 MR로 나눈다.
- 커밋에는 해당 목적에 필요한 파일만 명시적으로 포함한다.
- 브랜치의 구체적인 작업 내용과 변경 범위는 커밋과 MR 요약에 기록한다.

## 권장 디렉터리 구조

- `pages/`: Selenium Page Object
- `api/clients/`: API 요청 Client
- `tests/learner/`: 학습자 UI 테스트
- `tests/educator/`: 교육자 UI 테스트
- `tests/api/`: API 테스트
- `tests/**/test_data/`: 테스트 데이터와 의미 있는 상수
- `tests/conftest.py`: 여러 테스트 영역에서 공유하는 fixture와 pytest hook

## 실행

- 전체 학습자 테스트: `poetry run pytest -m learner`
- 전체 교육자 테스트: `poetry run pytest -m educator`
- 전체 API 테스트: `poetry run pytest tests/api`
- 관련 테스트를 먼저 실행한 뒤 영향 범위가 크면 전체 테스트를 실행한다.

## 보안

- `.env`의 계정 정보를 코드와 로그에 출력하지 않는다.
- `.env`를 수정하거나 Git에 추가하지 않는다.
- 데이터 생성·수정·삭제 테스트는 요청된 TC에만 구현한다.
